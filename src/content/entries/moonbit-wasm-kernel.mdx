WASM 的调用开销不高，真正难的是边界：宿主和内核各自认为内存长什么样，谁负责保证索引安全，线性内存增长时谁的视图作废。这些问题在纯 JS 里不存在，跨过去之后每一条都要有答案。

## 出口与握手

内核只导出稳定的 `dsp_*` 函数，另外导出一个 ABI 版本号。改动任何导出的语义或形状，版本号就加一。宿主启动时先拿版本号比对，再拿 `WebAssembly.Module.exports` 对一遍自己的接口表，两边对不上就在处理用户数据之前失败。

失败以值的形式过边界：`0` 表示拒绝请求，`-1` 表示句柄无效，布尔用 `1` 和 `0`。导出数组到达宿主时是它数据段的首地址，启动探针会双向验证一次这个约定，确认没问题才开始干活。

```ts
const abi = exports.dsp_abi();
if (abi !== KERNEL_ABI) throw new Error("stale kernel module");
```

## 三类存储

| 存储 | 生命周期 | 规则 |
| --- | --- | --- |
| Plan | 进程级，按窗长一份 | 只读并缓存 |
| Slot | 一次变换会话 | 池里固定六个，用完必须归还 |
| Arena | 一次 PGHI、RTISI 或元数据任务 | 持有各自的双精度与字节段 |

分三档是为了让容量可证明。Plan 覆盖 FFT 表，Slot 覆盖一次 STFT 帧，Arena 覆盖一次完整重建任务。三者都在启动或申请时确定尺寸，内核因此知道索引范围，热循环可以走无边界检查的访问。

这不是微调。在 release 构建里，对内核里那几种无法被证明安全的索引模式，带检查的访问测得慢 2 到 3 倍，读和写都一样。每一个无检查循环都由白盒测试覆盖，范围由 Plan、Slot 或 Arena 的容量保证。

## 视图会失效

上面三种存储都可能增长线性内存，而内存一增长，宿主手上所有的 `TypedArray` 视图就全部分离。规则只有一条：每次分配之后重新取视图，每次 `await` 之后也重新取。这条规则如果漏掉，症状是读到空数组，而不是报错。

## 让出消息循环

一次重建可能跑几百毫秒。内核每约 12 毫秒用一次性 `MessageChannel` 把控制权交回 Worker 消息循环，取消与进度事件因此能及时处理。通道用完立刻关闭，否则 Bun 或浏览器的事件循环会一直被它牵着，进程不退出。

## 门禁

内核和 TypeScript 参照实现跑同一份输入，比较整条数值链的输出，并要求总耗时低于实时的 `0.05×`。当前四档实测约 `0.007 / 0.006 / 0.005 / 0.002×` 实时。绝对时间随机器变，所以判定看同一轮里的比值。

白盒测试覆盖 FFT 往返、Parseval 关系、计划尺寸和池生命周期。这些是能证的；不能证的靠门禁卡住。
